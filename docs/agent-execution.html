Design note · swarn backend · jobs

How a job runs the agent, and why it runs it this way

The API never imports the agent. It starts one short-lived worker process per job, hands it a spec on stdin, and reads a stream of JSON events back on stdout. This page shows the moving parts, one job's lifetime, the pipe protocol, and the reasons behind each choice.

1 · The shape

Two kinds of process. The API process is long-lived and owns the queue, the database, object storage, and the browser connection. A worker process lives exactly as long as one job and is the only place the agent.* package is ever imported.

The supervisor is the only object that knows a job from queued to finished. Everything else either asks it (routes) or reports to it (the worker).

2 · One job, start to finish

Time flows down. The loop in the middle is where the job spends almost all of its life: the engine takes a step, the worker turns it into an event, the API stores it and pushes it to the browser.

  1. POST /jobs validates the request, writes a jobs row with status queued, and calls Supervisor.enqueue(job_id). The HTTP response returns immediately.
  2. The dispatch task takes the id off the queue and waits for a slot (a semaphore sized by job_concurrency, default 2). Only then does the job start.
  3. staging.pull creates ./work/<job_id>/ and downloads the workspace's files, prior sessions, datasets and knowledge from MinIO into the layout agent2 expects.
  4. The supervisor runs python -m swarn_backend.worker with pipes on stdin, stdout and stderr, in its own session group, with the staging directory as the working directory. The first stdin line is the WorkerSpec JSON.
  5. The worker sets every SWARN_* path variable to the staging directory, redirects sys.stdout to stderr, and only then imports agent2. JobRunner.run picks the engine from spec["method"]: react, team, aide, or eval.
  6. Before calling the engine the runner wires three hooks: a subscriber on agent2's session store (every step becomes a session_step event), a wrapped ApprovalBroker (questions become approval_request events), and a usage listener (token counts every half second).
  7. The supervisor reads stdout line by line. Each event is appended to job_events or the matching record table, then forwarded on the user's WebSocket as a channel: "job" or channel: "session" frame.
  8. Approvals and cancels travel the other way: the browser calls the API, the API writes a command line to the worker's stdin, and a reader thread inside the worker hands it to the broker or sets the stop event.
  9. When the engine returns, the worker emits one final done event with status, result, and usage, then exits. The supervisor's _finalize pushes the staging directory back to MinIO, records sessions and search runs, writes a usage_events row, sets the job's terminal status, and deletes the directory.

3 · The pipe protocol

Everything between the two processes is newline-delimited JSON. Defined in jobs/protocol.py; the worker side lives in worker/io.py.

4 · Why a subprocess, and why this shape

Each choice below answers a constraint that agent2 or the hosted setting imposes. The first one is the one that forces all the others.

The forcing constraint

agent2 fixes its paths at import time

Its paths module reads SWARN_DATA_ROOT and friends once, when first imported. A single API process could only ever point at one directory.

every job needs its own directory, every job needs its own interpreter. The worker's main sets the environment, then imports. The order is the whole trick.

Isolation

A bad job cannot take the API down

Engines pull in Docker sandboxes, Chroma, pandas, matplotlib, and long-running LLM loops. Crashes, leaks and hangs stay inside the worker.

the API only sees an exit code and a stderr tail, it can always record a clean failed status and move on to the next slot.

Fresh state

No state leaks between jobs

Dataset registries, session stores, usage trackers and thread-local brokers are process globals in agent2.

the process ends with the job, nothing has to be reset, and two users' jobs can never see each other's frames.

Local disk, remote truth

Pull, run, push

agent2 is file-based: workspace/, sessions/, runs/, knowledge/. MinIO is the durable store and Postgres the index.

the engine is never taught about object storage, the staging directory gives it the filesystem it already understands, and push reconciles afterwards. Files and datasets the engine produces mid-run are uploaded immediately from events, so a crash loses the directory but not what was already reported. Failed directories can be kept with keep_failed_workdirs; stale ones older than a day are swept at startup.

Transport

Plain pipes, newline JSON

No broker, no Redis, no HTTP callback. The worker's real stdout is duplicated for the protocol and sys.stdout is pointed at stderr, so any print inside an engine lands in the API log instead of corrupting the stream.

stdin and stdout exist the moment the child starts, ordering is guaranteed, back-pressure is free, and a dead parent shows up as EOF, which the worker treats as cancel. Lines over 64 MB are dropped rather than killing the reader.

Live and durable at once

Every event is a row and a frame

The supervisor appends each event to job_events with a per-job sequence number, then pushes it over the WebSocket.

a browser that reconnects can replay from GET /jobs/{id}?since=, and the record is complete even if nobody was watching.

Humans in the loop

Approvals cross the pipe both ways

The runner subclasses agent2's ApprovalBroker so a parked question is emitted as an event and its resolution is announced however it was answered. SWARN_AUTO_APPROVE is stripped from the worker's environment.

the approval card is the product. The API waits up to 2 seconds for the worker's acknowledgement and tells the caller if the engine was no longer waiting.

Backpressure and restarts

A queue, a semaphore, and stale-job recovery

One dispatch task, job_concurrency slots, one asyncio task per running child.

workers are not tracked outside the API process, a restart marks every running job as failed · server restarted instead of pretending it might finish.

The cancel ladder

Cancellation is cooperative first and forceful last, because a cooperative stop lets the engine close its sandbox and write its trace.
